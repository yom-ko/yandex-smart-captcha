# Agent context: Source of truth

This directory is the **only** place to edit canonical context for AI-agents.

The provider-specific files are generated by [`build-agent-context.sh`](../build-agent-context.sh) that is run automatically by the pre-commit hook in [`.githooks/`](../.githooks/).

| Source            | Generated outputs                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| `project.md`      | `AGENTS.md` `.claude/CLAUDE.md` `.github/copilot-instructions.md`                                  |
| `rules/<name>.md` | `.claude/rules/<name>.md` `.cursor/rules/<name>.mdc` `.github/instructions/<name>.instructions.md` |
| `skills/<name>/`  | `.claude/skills/<name>/` `.cursor/skills/<name>/` `.github/skills/<name>/`                         |

## Ownership

The following directories and files are **fully owned by the generator**:

- `AGENTS.md`
- `.claude/CLAUDE.md`
- `.github/copilot-instructions.md`
- `.claude/rules/`
- `.cursor/rules/`
- `.github/instructions/`
- `.claude/skills/`
- `.cursor/skills/`
- `.github/skills/`

> **Note:** Never manually create or edit files in those locations, as any changes will be overwritten on the next generator run.

Generation is all-or-nothing: everything is built in a temporary directory first, and the repository is only modified when the whole build succeeds. Installation is two-phase (every target is copied next to its destination first, then swapped in with a rename) and is rolled back if a swap fails, so a failure never leaves a mix of old and new files.

Key principles:

- Rules must be regular `.md` files, and each skill must be a directory containing `SKILL.md`.
- Rule and skill names may contain only lowercase ASCII letters, digits, `.`, `_` and `-`. They must start with a letter or digit and must not end with `.`.
- Hidden (dot-prefixed) entries in `rules/` and `skills/` are ignored, and `.DS_Store` files are never copied.
- Symlinks anywhere under `.agents/` are rejected, so outputs depend only on the repository content.

## Enabling the hook

Just set up the custom hooks path:

```bash
git config core.hooksPath .githooks
```

To ensure the reliable SSOT + "all-or-nothing" paradigm, the hook implements the following high-level logic:

```text
Staged changes in .agents/, the generator, or generated files?
    ├─ no → do nothing
    └─ yes
        ↓
        Do .agents/ or the generator have unstaged or untracked changes?
            ├─ yes → abort commit
            └─ no
                ↓
                Are there git-ignored files under .agents/?
                    ├─ yes → abort commit
                    └─ no
                        ↓
                        regenerate
                        ↓
                        stage generated files
                        ↓
                        commit
```

When `.agents/`, the generator script, or any generated target is staged, the hook regenerates the outputs and stages all managed targets, including deletions. It refuses to run if those sources have unstaged, untracked, or ignored untracked files that could affect generated output. The `.agents/` source directory must be a real directory, not a symlink.

> **Note:** After `git commit <path>`, Git may show the regenerated files as both staged and modified. The commit itself is correct; refresh the index by running `git add` on just those files (avoid `git add -A`, which would also stage unrelated changes).

Hooks can be bypassed with `--no-verify`, so use `--check` in CI as the safety net.

## Updating context directly

To update the agent context without committing any changes, just run the generator directly:

```bash
./build-agent-context.sh
```

To verify that the committed outputs match `.agents/` without modifying anything (eg. in a CI pipeline), run:

```bash
./build-agent-context.sh --check
```

## Writing path-dependent rules

> **Note:** Different AI providers (Claude, Cursor, Copilot, etc.) use different frontmatter keys to evaluate applicable paths. When creating or editing `rules/`, duplicate file patterns across `globs`, `paths`, and `applyTo` to ensure cross-provider compatibility.

```yaml
---
description: Rule description
globs: "**/*.dart"
paths:
  - "lib/src/*.dart"
  - "test/src/*.dart"
applyTo: "lib/src/*.dart,test/src/*.dart"
alwaysApply: false
---
```
